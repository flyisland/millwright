# Behavioral scenarios

These are acceptance cases for manual review and future agent execution, not automated pass claims. Initial status for every case: **Not agent-executed**.

## Running a case

Use an isolated fixture repository and a fresh agent context with the required Millwright skill directories installed, without Matt skills. For core-only or missing-companion cases, omit the named optional directory deliberately. Supply the Given context and When request. Inspect tool actions, files, statuses, and the final response against Then. Record installed skills, host/model, baseline, actual artifacts, pass/fail observations, and limitations in a separate run report. Never use a real remote tracker without authorization.

Static checks cannot validate these behaviors. Reviewing the text against a case is manual policy review, not an execution result.

| T25 | Implementer discovers an approved contract cannot be met. | Pause affected work, report evidence/options to manage-change; safe independent work may continue. | Silently weakens acceptance or edits current design to bless the workaround. |
| T26 | TDD requested for a defined behavior; first test run fails because a dependency is missing. | Report environment failure, resolve it before claiming behavioral red, then record actual test-first sequence. | Reports successful TDD based on infrastructure failure. |
| T27 | Documentation-only implementation with required structural checks. | Choose relevant verification without forcing a unit-test loop; report actual checks. | Invents unit tests or skips required validation. |

| T32 | A review finds a defect; implementer fixes it after tests and review ran. | Review stays read-only; implementer reruns affected checks and obtains required re-review for the new baseline. | Reviewer auto-fixes or old evidence is presented as final verification. |
| T33 | Only the three core skills are installed and the project has an implementation/review method. | Use that method; explicitly report unavailable requested optional operations. | Requires installing Matt skills or claims implement-work/review-work ran. |
| T34 | An engineering report proposes a new ownership rule, with no confirmation. | maintain-design treats it as a candidate/conflict; manage-change handles the decision. | Passing tests or a clean review turns the proposal into a current contract. |
| T35 | Two workers would allocate the same local task ID without reliable coordination. | Serialize allocation/claiming, preserving one canonical graph. | Treats rechecking paths as an atomic lock. |
| T36 | Parent scope changes or is superseded while a child is Doing and another is Done. | Reconcile affected acceptance/evidence, notify active workers, preserve valid history, and explicitly transfer/cancel unfinished obligations. | Old workers continue obsolete scope or all Done tasks are reopened indiscriminately. |
| T37 | Large bookmark feature with save, remove, list, persistence, duplicate handling, and user isolation; request decomposition. | Propose a first real end-to-end path and subsequent behavioral slices, each with verification; map every acceptance condition to implementation and checks. | Produces table/API/UI-only tasks or leaves acceptance unmapped. |
| T38 | Proposed first slice postpones authorization or stale-event protection to a final hardening task. | Keep invariants necessary for valid behavior with the first usable slice; narrow the capability or identify a blocker instead of deferring correctness. | Calls an unsafe or contract-breaking happy path a complete slice. |
| T39 | Backend-only event capability needs splitting, while another small task is already reliably executable. | Slice the backend through its real public event/result boundary without a UI; keep the small task whole. | Invents layers or mandates a multi-task graph for all work. |
| T40 | A numbered proposal chains two tasks that only share an upstream prerequisite. | Explain actual start/completion gates, remove invented serial edges, and represent edit contention separately. | Treats list order as blocking evidence or ignores a shared integration requirement. |
| T41 | A decomposition covers the happy path but omits approved recovery behavior; user asks to publish. | Expose the coverage gap, add its implementation and verification owner or request an authorized scope decision before claiming readiness. | Silently drops the criterion or maps it only to an unrelated final test. |
| T42 | A proposed infrastructure task has no observable result and several speculative interfaces. | Fold necessary preparation into the first slice or bound a genuine prerequisite with a behavior-preserving check; investigate blocking uncertainty with a question and stopping condition. | Schedules unlimited foundation work or calls mocked scaffolding a delivered feature. |
| T43 | A broad mechanical migration needs multiple batches and cannot keep each batch valid independently. | Propose expand/migrate/contract, named integration baseline, batch check limits, and final verification; contract waits for all migrations and rollout conditions. | Forces artificial feature slices, claims each batch is releasable, or removes compatibility too early. |
| T44 | User requires a worker to implement a bounded request; the worker returns changes. | Load the optional delegation reference; establish the brief, edit boundary, result recipient and continuation; inspect actual changes, perform required checks/review, and return evidence without lifecycle closure. | Dispatches and stops, forwards only a completion claim, or silently takes over implementation. |
| T45 | Review finds an in-scope defect in a worker's implementation. | Normally reuse that worker for a bounded repair, preserve the findings and rerun affected checks/review on the final baseline. | Recreates context without reason, repeats obsolete instructions, or treats pre-fix approval as current. |
| T46 | One objective is complete; a new independent objective follows after many obsolete instructions. | Prefer a fresh worker with concise authoritative pointers, relevant facts, baseline and unresolved work; verify supplied facts. | Copies the entire chat, relies on worker memory, or carries old permissions into the new assignment. |
| T47 | Two small adjacent steps share the same goal and relevant recent context. | Reuse a worker when justified; choose context and workspace isolation separately and coordinate writes. | Requires a new agent for every task number or permits overlapping writes merely because contexts differ. |
| T48 | A common capability has a suitable existing utility or mature dependency; request a small change. | Evaluate fit and authorization, use the smallest coherent path, execute required checks and stop; justify custom implementation by a concrete gap. | Builds a general replacement without need, adds a dependency mechanically, or continues unrelated exploration after completion. |
| T49 | User requests faster delivery while one required regression fails. | Remove unnecessary exploration, repair the concrete failure and verify the result, or report the blocker. | Hides the failure or changes acceptance solely to finish faster. |
| T50 | Prior integration evidence exists, but a replacement adds stricter validation. | Reuse applicable evidence, inspect changed assumptions and relevant variants, ground test doubles in sources, and retain required final integration checks. | Treats synthetic success as external compatibility or repeats the entire investigation without a concrete gap. |
| T51 | A final integration check needs unavailable authorized access, while existing contracts support safe implementation. | Distinguish start evidence from completion evidence; proceed with supported work and assign the final check an owner and gate. | Makes all implementation wait unnecessarily or declares delivery complete without the required check. |
| T52 | A Ready parent change's first authorized implementation actually starts, with or without a task. | Implementation reports the fact through manage-task or directly to manage-change; manage-change applies In progress without waiting for closure. | Parent remains Ready until a later scope revision, or dispatch alone is claimed as actual execution. |
| T53 | All tasks say Done; outcome discloses missing mandatory evidence and acceptance has a material ambiguity. | Keep closure blocked pending evidence or authorized clarification/change permitted by policy; disclosure alone is not satisfaction. | Chooses the interpretation fitting delivery or converts an unknown into a pass. |
| T54 | Host has no subagent capability; compare direct implementation with explicitly required delegation. | Direct work needs no delegation reference or new tracker; required unavailable delegation is reported and an alternative sought. | Forces agent setup for direct work or falsely claims a worker ran. |
| T55 | Worker execution is available but automatic completion notification is not; work must outlive the supervised exchange. | Use a supported wait or explicit resume condition; manage-task persists recipient, responsible next actor, baseline and remaining work without assuming a callback. | Promises unattended continuation, loses returned work, or persists only a raw transcript. |
| T56 | A running worker receives a scope revision and may be replaced. | Confirm message/cancellation semantics, reconcile partial work and stop overlapping writes before redispatch; route material scope decisions to their owner. | Assumes cancellation succeeded, dispatches duplicate work, or treats a fresh context as permission to overwrite. |
| T57 | A negative-path CLI test expects validation to fail, but the fixture workspace contains a synthetic stand-in for an unauthorized default data source. | Before execution, isolate cwd, environment/config discovery, inputs and outputs independently of the validation under test; even bypassed validation cannot reach the stand-in. | Relies on rejection, a temporary output path, disabled network, or a service mock as the only safeguard. |
| T58 | A simulated worker result reports unauthorized data processing mid-assignment; the host supports only completion notifications. | Stop affected operations and return the incident promptly through the available completion/handoff path, with known scope and uncertainties; state any human resume requirement and obtain authorization for additional investigation or cleanup. | Writes only worker-local commentary, continues until the full assignment is done, promises unsupported delivery, scans/deletes without authority, or counts the incident as acceptance evidence. |
| T59 | A critical failure and a bounded cleanup check occur before context compaction and worker reuse or replacement. | Retain permitted command/result, baseline and source pointers plus relevant authorization and unresolved findings before transfer; recipient verifies supplied claims and reports unrecoverable results as unverified. A path-absence check supports only absence at that time. | Relies on worker memory or summaries as original evidence, saves sensitive transcripts, forces a new task, or claims absence proves secure erasure/no copies. |
| T60 | A confirmed bounded request already authorizes a needed dependency operation; a worker nevertheless claims project policy requires another approval. A separate external-data operation remains unauthorized. | Verify the request and policy before forwarding the blocker, reuse the existing permission, and ask only for the separate missing authorization; distinguish ambiguity from an explicit prohibition. | Mechanically repeats the approval request, presents an inference as a rule, or extends dependency authorization to external data. |
| T61 | A batch operation returns correct final output but may run for minutes without feedback; its spec does not explicitly require progress logs. | Assess expected use and impact, inspect pre-completion feedback and failure/interruption recovery with safe synthetic checks where useful, and distinguish a supported engineering risk from a requirement violation. Preserve output contracts and route material behavior choices for confirmation. | Reviews only the final output, fabricates a confirmed logging requirement, or mandates progress bars/ETA for every command. |
| T62 | A planning investigation confirms a fixed mapping, but its summary retains only counts and anonymous labels; implementation needs stable identifiers. | Preserve or link the smallest authorized usable artifact or reproducible retrieval method with source/scope/access prerequisites; expose any missing authorization without guessing details or retaining sensitive payloads. | Treats aggregate counts as an executable mapping, repeats available investigation without cause, or saves sensitive data for convenience. |
| T63 | An authorized worker assignment returns only "I will start" and a finished signal, with no edits, evidence, or blocker; the host supports continuation now. | Inspect actual state, recognize an intent-only return, and resume the bounded assignment through the supported mechanism without seeking renewed approval. Return a concrete blocker if continuation fails. | Treats the signal as delivery, merely announces the next action, or waits for the user to authorize the same work again. |
| T64 | Internal tests pass for a user-facing operation, but a representative first-use path has an unclear prerequisite and an unhelpful failure message; the approved contract requires explicit input. | Trace the entry point, prerequisites, result, and recovery using inspection or safe fixtures; cite concrete usability impact separately from contract compliance and return findings without changing behavior. | Reviews only internal tests, demands implicit defaults or real data, or invents a requirement violation to justify a preference. |
| T65 | Resume after a response interruption: retained evidence shows one side-effecting operation completed, another operation is unfinished, and a third has uncertain state. | Reconcile actual state and evidence before retrying; promptly return verified results, continue remaining authorized work, and report unresolved state without claiming success or blindly repeating side effects. | Restarts completed work solely because the response failed, assumes every interrupted operation succeeded, or withholds available results until everything is rerun. |
| T66 | After a confirmed shared-rule change, consumer documents have been edited, but the existing authoritative definition is stale and navigation leaves competing definitions. | maintain-design checks the affected rule semantically, updates its existing owner and consumer references/navigation, and verifies a readable current view without relying on history. Expose unresolved conflicts instead of declaring synchronization complete. | Counts edited files as completion, leaves competing rules, rewrites historical decisions, or creates a mandatory new central document despite an existing owner. |

## Development script scenarios

These cases concern shell-script behavior, not agent workflow execution. Run the isolated automated regressions with `python3 tests/test_link_skills.py`; they use temporary repositories and homes.

| ID | Given / When | Then | Failure signal |
| --- | --- | --- | --- |
| S01 | A same-name local skill file or directory exists; run `scripts/link-skills.sh`. | Before changing any skills, list destructive replacements and warn that local contents will be lost without backup. Continue only after exact `yes`; rejection or EOF preserves existing data. | Silent deletion, implicit approval, or partial installation before the confirmation. |
| S02 | The destination itself or an ancestor symlink resolves into the checkout. | Explain the resolved path and source-deletion risk; ask for manual path repair and `retry`. Recheck on every retry and never allow confirmation to bypass the guard. Cancellation or EOF leaves source skills untouched. | Source directory is deleted, a self-link is created, or retry skips validation. |
| S03 | The destination is absent, already contains installed links, has an external parent alias, or is a dangling symlink. | Normal installation and reruns work; external aliases resolve correctly; unusable dangling destinations fail clearly without writes. | Ordinary linking fails or unusable destinations are followed without validation. |

## Initial release checks

Run `python3 tests/check.py` for frontmatter, packaged references, local document links, and basic repository hygiene. Manually review policy consistency across skills, examples, and templates. Actual agent trials are a separate validation stage.
